# 2026-10-20 真机录制告警诊断

本次交换配置中的视角绑定：DECXIN → global（YUYV）、LRCP → wrist（MJPG），
保留稳定设备路径、V4L2、640×480、30 FPS。两路同时读取 5 秒通过，8 项设备检查测试通过。
本次没有修改采样调度，也没有改写已有数据；配置交换只影响后续录制。
交换前录制的回合仍保留原有视角含义，不能直接与交换后的回合混用。

## Record loop is running slower

用户提供的 20:21:02 开始的日志包含 238 条慢周期告警，报告频率中位数为 27 Hz。
只读核对 `datasets/real/elfin_demo` 的 Parquet 与会话日志，按状态及动作的 float32 数值
唯一匹配全部 170 个已保存样本；没有把重置期间的样本计入各回合采样频率。

| episode | 帧数 | 主机首末采样跨度 | 数据集首末 timestamp 跨度 | 实际平均频率 |
|---|---:|---:|---:|---:|
| 0 | 87 | 3.2166 s | 2.8667 s | 26.736 Hz |
| 1 | 83 | 3.0864 s | 2.7333 s | 26.568 Hz |

会话样本的时间分解中位数：从 source 查询开始到 target 查询开始 33.419 ms，
target 查询耗时 3.113 ms，target 返回到下次 source 查询 0.683 ms。
主线程从相机缓存取帧耗时约 0.042 ms；它不是曝光耗时或图像年龄。

主要问题是 `ElfinWelding.measured_action()` 先等待一个完整目标采样周期，
再同步读取后继状态、写会话日志，随后原生录制流程再写数据。
SDK 后继查询与写入开销叠加到 33.3 ms 之后，导致周期约 37 ms。
首次编码等额外开销也可能增加抖动，现有日志不能将这些开销全部归因于 AV1 编码。

原生 `DatasetWriter.add_frame()` 仍按 `frame_index / fps` 自动生成时间戳；
这两个回合时间轴被压缩，回放速度约为实际的 1.122/1.129 倍。
数据可能仍可解码和参与训练，但速度、动作预测跨度对应的真实时长与 30 Hz 假设有偏差，
不能判为严格 30 Hz 合格。warning 本身不能证明文件损坏或确定丢帧数量。
其中“robot control might be unstable”是原生通用提示；本项目的 `send_action()` 只返回标签，
不会通过该接口改变由外部程序或示教器控制的机械臂运动。

后续应调整为连续采样、相邻实测样本配对，让后继采样与下一周期重叠，
减少串行等待及重复查询，并重新实测保存帧的间隔和抖动；仅屏蔽告警或修改 FPS 声明不能修复。

## Preset M12 is mapped to M10

本机日志显示 SVT-AV1 v3.0.0。该编码器版本将 M11–M13 映射到 M10，
这是[官方合并记录](https://gitlab.com/AOMediaCodec/SVT-AV1/-/merge_requests/2343)说明的行为。
实际使用 preset 10，不改变 AV1 编码格式，不表示视频损坏。
配置写着 preset 12 并不意味着编码器实际执行独立的 preset 12；对比压缩效果时还需核对编码器版本。

## 旧仓库与原生编码能力对照

进一步只读检查 `huayan_px` 的 record task、Huayan V2 适配器及保存的数据：

| 项目 | 旧仓库 | 当前项目 |
|---|---|---|
| LeRobot | 0.4.4 | 0.6.0 |
| 流式编码 | true | true，已经启用 |
| 编码设置 | vcodec=auto、encoder_threads=4 | AV1 软件编码、encoder_threads=2 |
| 旧数据实际码流 | welding_demo 两路均为 H.264 | elfin_demo 为 AV1 |
| 状态与动作配对 | 每周期一次 SDK 查询，使用前后两次观测构造增量 | 等待一个周期后再查询 target |

旧安装的 `lerobot_record.py` 也有相同的慢周期 warning，旧仓库没有删掉这项检查。
连续观测配对不额外阻塞一个周期，是它更容易满足 30 Hz 的重要原因；
没有历史采样时序，不能仅根据旧数据 metadata 的 30 FPS 断言其严格时序已经通过。
旧实现首帧使用零增量，动作是 7D；借鉴配对方式时仍需保留本项目的首尾实测标签、
回合边界及 9D 绝对动作契约，不能直接替换成旧数据定义。

本机 RTX 4060 Laptop、已有 Pixi dev 环境中的实测结果：

- 原生 `RGBEncoderConfig(vcodec="auto")` 选择 `h264_nvenc`，不会选择 AV1 NVENC。
- 使用原生 H.264 NVENC 选项、preset=12，内存中编码并解码 30 帧 640×480 RGB 成功。
- 底层 PyAV 的 `av1_nvenc` 使用 preset=p1、qp=30、g=2、bf=0，也通过同样的 30 帧检查。
- 当前 LeRobot 的允许列表不含 `av1_nvenc`，配置入口会直接拒绝；仅凭硬件支持不能直接使用。
- 部分 NVENC 默认预设的 B 帧设置与 GOP 2 冲突，参数必须一起验证，不能只改编码器名称。

这些检查没有读取机械臂、安装依赖、改写数据或改变当前 AV1 配置，也不是完整采集速率验收。
原生流式编码与硬件编码的职责见[官方流式编码文档](https://huggingface.co/docs/lerobot/main/en/streaming_video_encoding)。
GPU 编码可以降低 CPU 开销，但不能抵消 Robot 适配器内部的显式等待。
直接切换 auto 会将本机数据改为 H.264，不能通过现有 AV1 参考格式校验。
AV1 NVENC 需要薄配置适配，编码参数也须如实记录；后续应先修正连续采样调度，
再根据完整采集实测判断是否还需要硬件编码。

后续已实施连续观测配对，真实设备两段复测约 29.81/29.89 Hz，慢周期告警为 0，
详见[采样调度修正及实机结果](consecutive-capture-2026-10-20.md)。
